# PO The Grands

ระบบเปิด อนุมัติ และติดตามใบขอซื้อ (PO) สำหรับทีมจัดซื้อของ The Grands ทำงานแยกจากระบบ Grandhouse ทั้งซอร์สโค้ด บัญชีผู้ใช้ ฐานข้อมูล และการเผยแพร่ เว็บสำหรับพัฒนาในเครื่องทำงานที่ [http://localhost:4180](http://localhost:4180)

> สถานะปัจจุบัน: deploy schema และ `manage-user` ไป Supabase project PO แล้ว; ทดสอบ owner/office, disabled login, session reload, Supabase refresh และ offline recovery แล้ว; เว็บหลักที่ผู้ใช้ deploy คือ [PO The Grands บน Vercel](https://po-thegrands.vercel.app/) ตรวจไฟล์และ assets แล้วตรงกับ `dist/` ใน repo; เว็บ Sites เดิมยังคงเป็นรุ่นก่อนหน้าแบบ owner-only

## ระบบนี้ใช้ทำอะไร

PO The Grands ใช้แทนการส่งคำขอซื้อที่กระจัดกระจายอยู่ในแชตหรือกระดาษ โดยรวมข้อมูลสินค้า ผู้ขอซื้อ การอนุมัติ การรับสินค้า ใบกำกับภาษี และประวัติการดำเนินการไว้ในใบเดียว

เป้าหมายของระบบมีดังนี้

1. พนักงานจัดซื้อเปิดใบ PO พร้อมรายการสินค้าและราคา
2. เจ้าของเห็นคำขอของทุกคนและเป็นผู้อนุมัติหรือไม่อนุมัติ
3. พนักงานผู้เปิดใบยืนยันเมื่อได้รับสินค้าครบ
4. เจ้าของตรวจรับใบกำกับภาษีและปิดใบ PO
5. บัญชีจัดซื้อหลักดูภาพรวมของทุกคนและ Export รายงานรวมได้
6. ทุกขั้นมีผู้ดำเนินการ เวลา และสถานะที่ตรวจสอบย้อนหลังได้

ระบบนี้เป็น **Purchase Order workflow** ไม่ใช่ระบบคลังสินค้า ระบบบัญชี หรือระบบจ่ายเงิน

## ภาพรวมการทำงาน

```text
พนักงานเปิด PO
      ↓
เจ้าของอนุมัติ ─────→ ไม่อนุมัติ (จบใบพร้อมเหตุผล)
      ↓
พนักงานยืนยันรับสินค้าครบ
      ↓
เจ้าของตรวจรับใบกำกับภาษี
      ↓
ปิดใบ PO
```

หลักการสำคัญคือ ผู้ใช้แต่ละบทบาททำได้เฉพาะขั้นของตนเอง และสถานะต้องเดินตามลำดับ ไม่สามารถข้ามจาก “รออนุมัติ” ไป “ปิดใบ PO แล้ว” ได้

## บทบาทและสิทธิ์

ระบบมี 2 บทบาทหลัก และ 1 สิทธิ์พิเศษของบัญชีออฟฟิศ

| ความสามารถ | เจ้าของ | บัญชีออฟฟิศหลัก | บัญชีออฟฟิศทั่วไป |
|---|---:|---:|---:|
| ดูใบ PO ของทุกคน | ✓ | ✓ | — |
| ดูเฉพาะใบของตนเอง | ✓ ผ่านรายการรวม | ✓ เลือก “ของฉัน” | ✓ ค่าเริ่มต้นและบังคับสิทธิ์ |
| เปิดใบ PO | — | ✓ | ✓ |
| อนุมัติ / ไม่อนุมัติ | ✓ | — | — |
| ยืนยันรับสินค้า | — | ได้ทุกใบทั้งของออฟฟิศหลักและทั่วไป | เฉพาะใบของตน |
| ปิดใบหลังรับใบกำกับภาษี | ✓ | — | — |
| จัดการบัญชีออฟฟิศ | ✓ | — | — |
| ตั้งบัญชีหลัก | ✓ | — | — |
| จัดการรายการแผนก/สาขา | — | ✓ | — |
| ดูสรุปรายเดือนรวม | — | ✓ | — |
| Export Excel รวม | — | ✓ | — |

### เจ้าของ

- เห็นใบ PO ของพนักงานทุกคน
- อนุมัติหรือไม่อนุมัติใบที่รออนุมัติ
- การไม่อนุมัติต้องระบุเหตุผล
- ปิดใบ PO ได้เมื่อพนักงานยืนยันรับสินค้าแล้ว และเจ้าของยืนยันว่าได้รับใบกำกับภาษี
- สร้าง แก้ไข ตั้งรหัสผ่าน และปิดบัญชีออฟฟิศมีให้ยืนยันก่อนลบ
- เลือกว่าบัญชีใดเป็นบัญชีหลัก
- ไม่เห็นเมนูสรุปรายเดือน เพราะหน้าที่หลักคืออนุมัติและตรวจรับเอกสาร

### บัญชีออฟฟิศหลัก

- เป็นบัญชีจัดซื้อที่เจ้าของติ๊ก “ตั้งเป็นบัญชีหลัก”
- เปิดและติดตามใบ PO ของตนเองได้
- เห็นใบ PO ของพนักงานทุกคน
- สามารถรับของแทนบัญชีพนักงานคนอื่นได้
- สลับมุมมอง “ทุกคน” และ “ของฉัน” ได้
- จัดการรายชื่อแผนก/สาขา
- ดูสรุปรายเดือนและ Export รายงานรวม
- ไม่มีสิทธิ์อนุมัติ ปฏิเสธ หรือปิดใบ PO

### บัญชีออฟฟิศทั่วไป

- เปิดใบ PO ได้
- เห็นเฉพาะใบที่ตนเองเป็นผู้เปิด
- ยืนยันรับสินค้าได้เฉพาะใบของตนเองที่เจ้าของอนุมัติแล้ว
- ไม่เห็นข้อมูล PO ของพนักงานคนอื่น แม้เรียก API โดยตรง
- ไม่มีเมนูแผนก/สาขาและสรุปรายเดือน

| `pending` | รออนุมัติ | พนักงานเปิดใบแล้ว รอเจ้าของตัดสินใจ | เจ้าของ |
| `approved` | รอรับสินค้า | เจ้าของอนุมัติแล้ว รอผู้เปิดใบรับสินค้า | ผู้เปิดใบ |
| `received` | รอใบกำกับภาษี | ได้รับสินค้าครบแล้ว รอเจ้าของตรวจเอกสาร | เจ้าของ |
| `closed` | ปิดใบ PO แล้ว | ตรวจรับสินค้าและใบกำกับภาษีครบ | ไม่มี |
| `rejected` | ไม่อนุมัติ | เจ้าของไม่อนุมัติ พร้อมเหตุผล | ไม่มี |

สถานะ `closed` และ `rejected` เป็นสถานะสิ้นสุด ไม่มีปุ่มย้อนกลับหรือแก้สถานะในระบบปัจจุบัน

## ขั้นตอนเปิดและดำเนินการ PO

### 1. เปิดใบ PO

บัญชีออฟฟิศกดเมนู **เปิดใบ PO** แล้วกรอกข้อมูลดังนี้

- วันที่ใบ PO ค่าเริ่มต้นเป็นวันที่ปัจจุบัน
- แผนก/สาขาของสินค้าแต่ละรายการ
- ชื่อสินค้า
- รายละเอียดหรือสเปค
- แหล่งซื้อ เช่น ร้านค้า ผู้ขาย หรือเว็บไซต์
- จำนวน รองรับทศนิยมสูงสุด 3 ตำแหน่ง
- หน่วย เป็นข้อความอิสระ เช่น ชิ้น กล่อง แพ็ก ชุด เครื่อง หรือกิโลกรัม
- ราคาต่อหน่วย รองรับทศนิยม 2 ตำแหน่ง
- เลือก VAT 7% หรือ NON VAT
- หมายเหตุเพิ่มเติม

หนึ่งใบมีสินค้าได้ 1–50 รายการ แต่ละรายการเลือกแผนก/สาขาและภาษีแยกกันได้

### 2. ตรวจทานก่อนส่ง

ก่อนเปิดใบจริง ระบบแสดงหน้าตรวจทานซึ่งมี

- วันที่ PO
- แผนก/สาขา
- รายการสินค้าและสเปค
- จำนวนพร้อมหน่วย
- ราคาต่อหน่วย
- ประเภทภาษี
- ยอดก่อน VAT เฉพาะรายการ VAT
- VAT รวม
- ยอดรวมสุทธิ

ผู้ใช้สามารถกลับไปแก้ไขได้ หากยืนยันแล้วสินค้าและราคาในใบเดิมจะไม่สามารถแก้ไขผ่านหน้าเว็บ

### 3. เจ้าของอนุมัติหรือไม่อนุมัติ

- **อนุมัติ:** ใบเปลี่ยนเป็น “รอรับสินค้า”
- **ไม่อนุมัติ:** ต้องกรอกเหตุผล ใบเปลี่ยนเป็น “ไม่อนุมัติ” และสิ้นสุด

### 4. ยืนยันรับสินค้า

ผู้เปิดใบกด **ได้รับสินค้าครบแล้ว** และติ๊กยืนยัน ระบบเปลี่ยนเป็น “รอใบกำกับภาษี”

ระบบปัจจุบันรองรับเฉพาะการรับสินค้าครบทั้งใบ ยังไม่รองรับการรับบางส่วน

### 5. ตรวจรับใบกำกับภาษีและปิด PO

เจ้าของติ๊กยืนยันว่า "ได้รับและตรวจสอบใบกำกับภาษีแล้ว" จากนั้นกดปิด PO ใบจะเปลี่ยนเป็น “ปิดใบ PO แล้ว”

ขั้นนี้ใช้กับทั้งรายการ VAT และ NON VAT เพื่อให้ทุกใบผ่านการตรวจเอกสารก่อนปิด

## ข้อมูลที่เก็บในใบ PO

ข้อมูลระดับใบประกอบด้วย

- UUID ภายในระบบ
- เลข PO เช่น `PO-2026-000001` หรือ `DEMO-2026-00001`
- วันที่ใบ PO
- เวลาสร้างจากระบบ
- UUID และชื่อบัญชีผู้เปิด
- แผนก/สาขา
- สถานะปัจจุบัน
- ยอดฐาน ยอด VAT และยอดสุทธิเป็นหน่วยสตางค์
- เหตุผลที่ไม่อนุมัติ
- เวลาที่อนุมัติ รับสินค้า และปิดใบ
- ตัวเลข `version` สำหรับป้องกันการทำงานจากข้อมูลเก่า

ข้อมูลระดับสินค้าแต่ละรายการประกอบด้วย

- ชื่อสินค้า
- รายละเอียด/สเปค
- แหล่งซื้อ
- จำนวน
- หน่วย
- ราคาต่อหน่วยที่ผู้ใช้กรอก
- VAT 7% หรือ NON VAT
- ฐานราคา ภาษี และยอดรวมของรายการ
- หมายเหตุ

ทุก action จะสร้างประวัติแยกซึ่งเก็บผู้ทำ ชื่อผู้ทำ action เหตุผล และเวลาจาก server

## หลักการคำนวณ VAT

ราคาที่กรอกคือ **ราคาสุทธิต่อหน่วยรวม VAT แล้ว** เมื่อเลือก VAT 7% ระบบถอด VAT ด้วยสูตร 7/107

```text
ยอดรวมรายการ = จำนวน × ราคาต่อหน่วย
ฐานก่อน VAT = round(ยอดรวมรายการ × 100 / 107)
VAT = ยอดรวมรายการ − ฐานก่อน VAT
```

ระบบปัดเศษระดับรายการเป็นสตางค์แบบ half-up แล้วจึงรวมยอดทั้งใบ

### ตัวอย่างรายการ VAT

ราคาสุทธิ 4,500.00 บาท

```text
ฐานก่อน VAT = 4,205.61 บาท
VAT 7%       =   294.39 บาท
ยอดสุทธิ     = 4,500.00 บาท
```

### ตัวอย่างรายการผสม VAT และ NON VAT

| รายการ | ประเภท | ยอดสุทธิ | นำมาถอด VAT หรือไม่ |
|---|---|---:|---:|
| หม้อนึ่ง | VAT 7% | 4,500.00 | ✓ |
| ถุงซิป | NON VAT | 100.00 | — |

ผลสรุป:

```text
รวมก่อน VAT (เฉพาะรายการ VAT) = 4,205.61 บาท
VAT รวม                         =   294.39 บาท
ยอดรวมสุทธิ                     = 4,600.00 บาท
```

รายการ NON VAT ไม่ถูกนำมาถอด VAT แต่ยังรวมอยู่ในยอดรวมสุทธิ

## หน้าจอและเมนู

### เข้าสู่ระบบ

- โหมด Supabase: เจ้าของเข้าด้วยอีเมล พนักงานเข้าด้วยชื่อบัญชี เช่น `purchase.fai01`
- ชื่อบัญชีพนักงานจะถูกแปลงเป็นอีเมลภายในรูปแบบ `ชื่อบัญชี@po.thegrands.local`
- รหัสผ่านออฟฟิศใช้ตัวอักษรหรือตัวเลขได้ อย่างน้อย 6 ตัวอักษร
- รหัสผ่านเจ้าของในโหมดสาธิตต้องมีอย่างน้อย 6 ตัวอักษร

### ใบขอซื้อทั้งหมด

แสดง

- จำนวนใบตามสถานะ
- ตัวกรองสถานะ
- ตัวกรอง “ทุกคน / ของฉัน” สำหรับบัญชีหลัก
- เลข PO ชื่อสินค้าแรก จำนวนรายการเพิ่มเติม ผู้เปิด วันที่ สถานะ และยอดรวม
- เส้นติดตามขั้นตอน เปิด PO → อนุมัติ → รับสินค้า → ปิด PO
- แบ่งหน้า 10 ใบต่อหน้า

### รายละเอียด PO

แสดงข้อมูลหัวใบ สถานะ เส้นขั้นตอน รายการสินค้า สรุปยอด ปุ่ม action ที่ตรงกับบทบาท และประวัติการดำเนินการทั้งหมด

### แผนก/สาขา

เห็นเฉพาะบัญชีหลัก ใช้เพิ่มหรือลบรายการที่นำไปค้นหาในช่องแผนก/สาขาตอนเปิด PO

### สรุปรายเดือน

เห็นเฉพาะบัญชีหลัก เลือกเดือนได้ และโหลดข้อมูลใหม่ทันทีเมื่อเปลี่ยนเดือน

### ผู้ใช้งาน

เห็นเฉพาะเจ้าของ ใช้สร้างบัญชีออฟฟิศ เปลี่ยนรหัสผ่าน กำหนดบัญชีหลัก และลบบัญชี

การลบบัญชีใน Supabase เป็นการปิดการเข้าสู่ระบบและทำ soft delete โปรไฟล์ ประวัติ PO เดิมยังอยู่

### การเชื่อมต่อ

แสดงสถานะว่ากำลังใช้โหมดสาธิตหรือเชื่อม Supabase แล้ว

## การแจ้งเตือน

ปุ่มกระดิ่งแสดงจำนวนการแจ้งเตือนที่ยังไม่ได้อ่าน

| เหตุการณ์ | ผู้รับแจ้งเตือน |
|---|---|
| พนักงานเปิด PO | เจ้าของทุกบัญชีที่ยังใช้งาน |
| เจ้าของอนุมัติ | ผู้เปิดใบ PO |
| เจ้าของไม่อนุมัติ | ผู้เปิดใบ PO |
| ผู้เปิดใบยืนยันรับสินค้า | เจ้าของทุกบัญชีที่ยังใช้งาน |
| เจ้าของปิด PO | ผู้เปิดใบ PO |

เมื่อเปิดแผงแจ้งเตือน รายการที่มองเห็นจะถูกทำเครื่องหมายว่าอ่านแล้ว และกดการแจ้งเตือนเพื่อไปยังรายละเอียด PO ได้

## สรุปรายเดือนและ Excel

รายงานนับยอดสั่งซื้อเฉพาะใบสถานะ

- รอรับสินค้า (`approved`)
- รอใบกำกับภาษี (`received`)
- ปิดใบ PO แล้ว (`closed`)

ใบที่รออนุมัติและไม่อนุมัติยังแสดงจำนวน แต่ไม่รวมมูลค่าในยอดสั่งซื้อ

ไฟล์ Excel มี 2 ชีท

1. **สรุปรายเดือน** — เดือน ยอดสั่งซื้อรวม จำนวนใบที่อนุมัติแล้ว จำนวนรออนุมัติ และจำนวนไม่อนุมัติ
2. **รายการสินค้า** — เลข PO วันที่ ผู้เปิด แผนก/สาขา สถานะ ชื่อสินค้า สเปค แหล่งซื้อ หมายเหตุ จำนวน หน่วย ราคา ภาษี ฐาน VAT และยอดรวม

ไม่มีชีท “รายการ PO” แยก เพราะสถานะและข้อมูลหัวใบถูกใส่ไว้ในชีทรายการสินค้าแล้ว

## บัญชีหลักและบัญชีทั่วไป

`can_export_report` เป็นสิทธิ์ที่กำหนดว่าบัญชีออฟฟิศเป็นบัญชีหลักหรือไม่

- `true`: เห็น PO ทุกคน กรองของตนเองได้ จัดการแผนก และ Export รายงานรวม
- `false`: เห็นเฉพาะ PO ที่ตนเองเปิด

เจ้าของเป็นผู้ให้หรือถอดสิทธิ์นี้ผ่านหน้า “ผู้ใช้งาน” ระบบไม่ได้ผูกสิทธิ์กับชื่อ `purchase.fai01` ในฐานข้อมูลจริง แม้ชื่อนี้จะเป็นตัวอย่างบัญชีหลักที่ใช้ระหว่างพัฒนา

## โหมดสาธิตกับโหมด Supabase

### โหมดสาธิต

ระบบเข้าโหมดนี้เมื่อ `dist/config.js` ยังไม่มี Project URL หรือ Publishable key

- บัญชีและ PO เก็บใน `localStorage` ของ browser เครื่องนั้น
- รีเฟรชหน้าแล้วข้อมูลใหม่ยังอยู่
- ข้อมูลไม่แชร์ข้ามเครื่องหรือข้าม browser profile
- เลขใบขึ้นต้น `DEMO-`
- รหัสผ่านสาธิตถูก hash ด้วย PBKDF2 ก่อนเก็บ
- เหมาะสำหรับทดลองหน้าจอและ flow เท่านั้น
- การล้าง Site Data, Local Storage หรือ browser profile จะทำให้ข้อมูลสาธิตหาย

### โหมด Supabase

ระบบเข้าโหมดนี้เมื่อใส่ `supabaseUrl` และ `publishableKey` ครบ

- Authentication และข้อมูลอยู่บน Supabase
- ผู้ใช้หลายเครื่องเห็นข้อมูลตามสิทธิ์เดียวกัน
- เลขใบขึ้นต้น `PO-`
- เวลาและยอดรวมสำคัญคำนวณซ้ำที่ฐานข้อมูล
- Row Level Security ป้องกันการอ่านข้อมูลเกินสิทธิ์
- Edge Function ใช้จัดการบัญชีออฟฟิศโดยไม่เปิดเผย Secret key
- หาก Supabase ติดต่อไม่ได้ ระบบแสดงข้อผิดพลาดและไม่ fallback ไปข้อมูลสาธิต

ข้อมูลสาธิตใน browser **ไม่ย้ายเข้า Supabase อัตโนมัติ** ต้องทำ migration โดยผูก `created_by` กับ UUID ของบัญชีจริงก่อน

## โครงสร้างระบบ

```text
Browser
  ├─ dist/app.js       หน้าจอ การนำทาง ฟอร์ม และ interaction
  ├─ dist/domain.js    validation สูตรเงิน สถานะ และกฎธุรกิจ
  ├─ dist/api.js       Auth, REST, RPC, Edge Function และ demo adapter
  ├─ dist/export.js    สร้างไฟล์ Excel ด้วย ExcelJS
  └─ dist/style.css    รูปแบบหน้าจอ responsive
          │
          ▼
Supabase
  ├─ Auth              บัญชีและ session
  ├─ PostgREST         อ่านตารางภายใต้ RLS
  ├─ PostgreSQL RPC    create_po, act_on_po, po_counts, monthly_po_report
  └─ Edge Function     manage-user สำหรับเจ้าของจัดการบัญชี
```

เว็บเป็น static frontend ไม่มี application server ที่เก็บ secret ตัว `server.mjs` ใช้เสิร์ฟไฟล์ในเครื่องเท่านั้น

## โครงสร้างฐานข้อมูล

### `profiles`

เก็บโปรไฟล์และสิทธิ์ที่จับคู่กับ `auth.users`

- `id` — UUID เดียวกับ Auth user
- `login_email` — อีเมลภายใน
- `login_name` — ชื่อที่ใช้เข้าสู่ระบบของพนักงาน
- `display_name` — ชื่อที่บันทึกในประวัติ
- `role` — `owner` หรือ `office`
- `can_export_report` — สิทธิ์บัญชีหลัก
- `deleted_at` — เวลาปิดบัญชี

### `purchase_orders`

เก็บหัวใบ PO ยอดรวม สถานะ เวลา workflow และ version รวมทั้ง `items` แบบ JSONB ซึ่งเป็น snapshot สำหรับหน้าเว็บเดิมและรายงาน รายการสินค้าแก้ไขโดยตรงไม่ได้

### `departments` และ `po_items`

`departments` เก็บรายการแผนก/สาขา บัญชีออฟฟิศหลักเพิ่มหรือเก็บเข้าคลังได้ การเก็บเข้าคลังไม่ทำให้ประวัติใบเก่าหาย `po_items` เก็บสินค้าแต่ละบรรทัดพร้อมแผนก/สาขา จำนวน หน่วย ราคา และ VAT โดยอ้างอิงหัวใบ PO และแผนก การเปิด PO บันทึกทั้ง `po_items` และ JSONB snapshot ใน transaction เดียว

### `po_events`

เก็บประวัติ create, approve, reject, receive และ close แบบเพิ่มอย่างเดียว

### `notifications`

เก็บการแจ้งเตือนแยกตามผู้รับและ PO พร้อม `read_at`

### `po_commands`

เก็บ request UUID, payload และผลลัพธ์ เพื่อให้การกดซ้ำหรือ retry คำขอเดิมไม่สร้างรายการซ้ำ

## ความปลอดภัยและการควบคุมสิทธิ์

- Anonymous ไม่มีสิทธิ์อ่านข้อมูล
- ผู้ใช้ที่ไม่มี profile เข้าใช้งานข้อมูลไม่ได้
- เจ้าของและบัญชีหลักอ่าน PO ทุกคนได้
- บัญชีทั่วไปอ่านเฉพาะ PO ที่ `created_by` เป็น UUID ของตนเอง
- บัญชีทั่วไปยืนยันรับสินค้าได้เฉพาะ PO ที่ตนเปิด บัญชีหลักยืนยันแทนได้ และบัญชีที่ปิดใช้งานเรียก RPC ไม่ได้
- สิทธิ์อ่าน `po_items` ตามสิทธิ์อ่านหัวใบ และการจัดการ `departments` ทำผ่าน RPC ของบัญชีหลัก
- ประวัติ PO ใช้เงื่อนไขเดียวกับสิทธิ์อ่านหัวใบ
- การแจ้งเตือนอ่านและแก้ `read_at` ได้เฉพาะผู้รับ
- Browser ไม่มีสิทธิ์ insert/update/delete ตารางธุรกรรมโดยตรง
- การสร้าง PO และเปลี่ยนสถานะต้องผ่าน PostgreSQL RPC
- รายงานรวมตรวจ `role='office'` และ `can_export_report=true` ที่ฐานข้อมูล
- การจัดการบัญชีตรวจบทบาทเจ้าของซ้ำใน Edge Function
- Publishable/Anon key ใส่ใน browser ได้เมื่อ RLS เปิดอยู่
- Service Role/Secret key ห้ามใส่ใน `dist/`, Git หรือหน้าเว็บ เพราะข้าม RLS ได้

## การป้องกันข้อมูลซ้ำและสถานะชนกัน

### Idempotency

ทุกคำสั่งสร้าง PO หรือเปลี่ยนสถานะส่ง request UUID หาก network timeout แล้วผู้ใช้ retry ด้วย UUID เดิม ฐานข้อมูลจะคืนผลเดิมแทนการสร้างซ้ำ

### Version control

แต่ละใบมีเลข `version` เมื่อ action สำเร็จเลขจะเพิ่ม หากสองหน้าจอเปิดใบเดียวกันและอีกหน้าดำเนินการไปแล้ว หน้าที่ถือ version เก่าจะถูกปฏิเสธและต้องโหลดใหม่

### Transaction

การตรวจข้อมูล คำนวณยอด สร้างหัวใบ บันทึกประวัติ และสร้าง notification อยู่ใน transaction เดียว หากขั้นใดล้มเหลวจะ rollback ทั้งชุด

## แก้ปัญหาเบื้องต้น

### เว็บเปิดไม่ได้

ตรวจว่า `npm start` ยังทำงานและไม่มีโปรแกรมอื่นใช้ port 4180

```powershell
npm start
```

### เว็บยังเป็นโหมดสาธิต

ตรวจ `dist/config.js` ว่ามีทั้ง `supabaseUrl` และ `publishableKey` แล้วรีสตาร์ต server

### เข้าระบบได้แต่แจ้งว่าไม่มีสิทธิ์

Auth user มีอยู่ แต่ไม่มีแถว UUID เดียวกันใน `public.profiles` หรือ profile ถูกใส่ `deleted_at`

### เจ้าของเปิดหน้าผู้ใช้ไม่ได้

ตรวจว่า Edge Function `manage-user` deploy แล้ว, `ALLOWED_ORIGINS` ตรงกับ origin ของเว็บ และ profile เป็น `role='owner'`

### พนักงานเห็น PO คนอื่น

หยุดใช้งาน production ชั่วคราว แล้วตรวจว่า schema/RLS เป็นเวอร์ชันล่าสุด บัญชีทั่วไปต้องมี `can_export_report=false`

### รายงานหรือเมนูแผนกไม่ขึ้น

บัญชีนั้นต้องมี `role='office'`, `can_export_report=true` และ `deleted_at is null`

### รายการ demo หาย

ตรวจว่าไม่ได้ล้าง Site Data หรือเปลี่ยน browser profile ข้อมูล demo ไม่ได้อยู่ในโฟลเดอร์โปรเจกต์

### ตัวเลข VAT ไม่ตรง

ตรวจว่าราคาที่กรอกเป็นราคาสุทธิรวม VAT ต่อหน่วย และติ๊ก VAT เฉพาะรายการที่มี VAT รายการ NON VAT จะรวมในยอดสุทธิแต่ไม่รวมใน “รวมก่อน VAT (เฉพาะรายการ VAT)”
